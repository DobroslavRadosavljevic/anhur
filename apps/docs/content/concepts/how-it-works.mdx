Anhur is a build-time content pipeline. It does not fetch remote CMS data at request time.

## Pipeline

1. **Load** — find files for each collection/singleton (Markdown/MDX front matter, YAML, JSON, or custom loaders)
2. **Validate** — run each document through your Zod schema
3. **Process** — optional MDX/Markdown compile, asset copy, references
4. **Transform** — per-document `transform`, drafts/skips, then project `prepare`
5. **Views** — optional `defineView` / `defineIndex` / `defineGroup` (filter, key maps, groups)
6. **Generate** — write modules under `.anhur/generated`
7. **Integrate** — optional `integrations` (e.g. Orama search index), then `complete`
8. **Import** — your app uses `anhur/generated` (and any integration outputs)

With [`@anhur/vite`](/packages/vite), steps 1–7 run on `vite dev` / `vite build` and again when content files change. With the [CLI](/getting-started/cli), you run `anhur build` or `anhur watch` yourself.

## Mental model

Think of each collection as a typed table of rows, and each content file as a row. Schemas define columns. Generated exports are the query API:

| You write                        | You get                                              |
| -------------------------------- | ---------------------------------------------------- |
| `name: "posts"`                  | `allPosts`, `getPost`, `Post`, …                     |
| `name: "settings"` (singleton)   | `settings`, optional `getSettings` / locale variants |
| `defineView` / `Index` / `Group` | `allFeatured…`, `productBySku`, `productsByCategory` |

## What Anhur is not

- Not a page router — you still own routes and UI
- Not a WYSIWYG CMS — authors edit files (or whatever puts files in the repo)
- Not a Markdown renderer by itself — MDX/HTML come from opt-in packages
